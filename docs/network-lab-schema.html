Network lab: pfSense, Pi-hole e Lubuntu

Sotto-laboratorio riproducibile del repo manzolo/kvm-lab · rete isolata lab-lan, dominio qlan · stato verificato il 6 settembre 2026

Tre macchine virtuali KVM ricreano una piccola rete aziendale su uno switch isolato dell'host: un firewall/router che fa NAT verso Internet, un resolver DNS con filtro pubblicità che distribuisce anche gli indirizzi via DHCP, e un client desktop. Tutto si installa da zero senza interazione e si può distruggere e ricreare in una ventina di minuti.

2. I tre componenti

pfSense · firewall e gateway

FreeBSD, pfSense CE 2.7.2, ZFS, console seriale

  • Fa NAT: tutto ciò che esce da lab-lan viene mascherato con l'IP WAN preso dalla rete default.
  • Regole LAN: "allow LAN to any" di default, più due regole ereditate dal vecchio firewall (blocco SSH verso .1.50, un blocco di test disabilitato).
  • DHCP LAN disabilitato: lo fa Pi-hole.
  • Unbound attivo su .1 ma usato solo dal firewall stesso; il DNS di sistema è .10.
  • GUI web in HTTP su http://192.168.0.1, utenti admin e VM_USER.

Pi-hole · DNS e DHCP

Ubuntu Server 22.04.5, Pi-hole core 6.4.3, FTL 6.7

  • Resolver per tutta la LAN con blocklist StevenBlack.
  • Upstream: OpenDNS 208.67.222.222 e .220.220, raggiunti attraverso pfSense.
  • 18 record A locali e 3 CNAME nel dominio qlan (tabella al §4).
  • DHCP per gli ospiti occasionali: pool .150–.199, lease 24 h, gateway .1, DNS .10, dominio qlan.
  • GUI web su http://192.168.0.10/admin/, password VM_PASS.

Lubuntu · client

Ubuntu Server 22.04.5 + lubuntu-desktop, LXQt, autologin

  • IP statico .100, gateway .1, DNS .10: rappresenta la postazione utente.
  • Nome interfaccia fissato a enp1s0 dal MAC, così non cambia se si aggiungono device.
  • Cartella storage/shared dell'host montata su /mnt/shared (virtiofs), link ~/shared e sul desktop.
  • Boot in circa 7 secondi; il guest agent QEMU permette i controlli da host.

4. Dominio qlan e flusso DNS

Ogni client chiede a Pi-hole. Se il nome è nel dominio locale Pi-hole risponde direttamente dai suoi record; altrimenti filtra il nome contro la blocklist e, se non è bloccato, lo chiede a OpenDNS passando dal NAT di pfSense. Unbound su pfSense non conosce qlan: chiedere a .1 un nome locale dà NXDOMAIN, ed è il comportamento atteso.

6. Come si costruisce e si ricrea

Tutto parte da network-lab/profile.json (indirizzi, dominio, pool DHCP, upstream) e dai file in network-lab/: configurazione XML pfSense ricavata dal vecchio firewall, record e liste Pi-hole, script di primo avvio. Credenziali in scripts/lab.env (VM_USER, VM_PASS), fuori dal repo.

make network-up          # crea lo switch lab-lan (senza DHCP libvirt)
make network-install     # pfSense → Pi-hole → Lubuntu, tutto da zero (~15–20 min)

bash scripts/install-pfsense.sh     # oppure una VM alla volta
bash scripts/install-pihole.sh
make lab-lubuntu22

bash scripts/clean-vm.sh pi-hole    # rimuove VM + SOLO il suo qcow2 (mai --remove-all-storage)
make network-attach VM=nome         # collega un'altra VM spenta alla LAN

L'installer rifiuta di sovrascrivere una VM o un disco esistente: prima si pulisce, poi si reinstalla. Sequenza interna per le due VM Ubuntu: autoinstall sulla rete default (serve Internet per i pacchetti e per l'installer Pi-hole), primo avvio con bootstrap via guest agent, sostituzione del netplan con l'IP statico della LAN, spegnimento, spostamento della NIC su lab-lan, riavvio. pfSense invece nasce già con due NIC e la sua configurazione completa viene scritta dall'installer FreeBSD.

Perché è tutto isolato. lab-lan non ha forward né servizi libvirt: senza pfSense acceso i client non escono e senza Pi-hole non risolvono nulla. È voluto: lo scopo è vedere cosa succede quando manca un pezzo, cambiare regole sul firewall o le liste DNS e osservare l'effetto sul client, senza toccare la rete vera dell'host.
